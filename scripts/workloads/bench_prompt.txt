Design notes: "logsift", a log filtering tool

Purpose. logsift reads application log files and prints only the lines that matter to the person on call. Teams keep many services, each with its own log format, and the people who answer alerts at night do not have time to remember the format of every service. The tool should let them type one short command and see the errors, the warnings that came just before the errors, and nothing else.

Inputs. The tool takes one or more file paths, or reads standard input when no path is given. Files may be plain text or gzip compressed; the tool decides by reading the first two bytes, not by the file name. A file can be very large, tens of gigabytes, so the tool must never load a whole file into memory. It reads line by line with a fixed buffer. A line longer than the buffer is cut, and the rest of that line is skipped until the next newline. The tool counts how many lines were cut and reports the count at the end.

Formats. Each service describes its log format in a small text file called a profile. A profile says where the timestamp is, where the level is, and what words mean "error" and "warning" for this service. The tool ships with profiles for the common formats: a JSON object per line, the classic "date level message" layout, and the systemd journal export. If no profile is given, the tool tries each built-in profile on the first two hundred lines and picks the one that parses the most lines. If two profiles tie, it picks the first one in alphabetical order and prints a warning that names both.

Filtering. The user chooses a minimum level, error by default. For each line at or above that level, the tool prints the line and also the previous N lines of context, where N is five by default. Context lines are kept in a ring buffer so that memory use stays constant. If two matching lines are close together, their context windows overlap, and the tool must not print any line twice. Between two groups of printed lines that are not adjacent in the file, the tool prints a separator line with the number of lines that were skipped.

Time ranges. The user can give a start time and an end time. Timestamps in the file are parsed with the format from the profile. A timestamp without a time zone is read as UTC unless the profile says otherwise. Lines without a timestamp, such as the later lines of a stack trace, belong to the most recent line that had one. The tool assumes that timestamps in a file never go backwards; when it sees a timestamp after the end time, it stops reading that file. This makes a query for "the last ten minutes of yesterday" fast on a large file only if the tool can skip to the right place, so for plain text files it does a binary search on byte offsets, moving forward to the next newline after each jump. For gzip files it cannot seek, so it reads from the start.

Multiple files. When several files are given, the tool merges their output by timestamp so that the user sees one timeline. It keeps one open reader per file and repeatedly prints the line with the smallest timestamp. Each printed line is prefixed with a short name for its file. The number of files is limited only by the number of file handles the operating system allows.

Output. By default the output is plain text, with the level colored when standard output is a terminal. With a flag, the output is one JSON object per line, with the fields time, level, file, line number and message. The tool exits with status 0 if it printed at least one matching line, 1 if it found none, and 2 on any error, so that it can be used in shell scripts the same way grep is used.

Performance goals. On a laptop the tool should filter one gigabyte of plain text per second per core. It uses one thread per input file for reading and parsing, and one thread for merging and printing. Parsed lines travel between the threads on bounded queues. If the printing thread is slow, for example because the terminal is slow, the reading threads block on the full queues and memory use stays bounded.

Error handling. A line that does not parse under the chosen profile is treated as a continuation of the previous line. If more than half of the first thousand lines fail to parse, the tool stops and tells the user that the profile is probably wrong. A file that disappears while it is being read, which happens with log rotation, ends that reader without an error. A file that cannot be opened at the start is an error, and the tool exits with status 2 before printing anything.

Open questions. Should the tool follow a file that is still being written, like "tail -f"? Should the context include lines after a match as well as before? Should profiles be allowed to run a user-supplied regular expression on every line, given the risk of very slow patterns?
